# Continuum performance audit

Audit date: 9 October 2026. This document records the original local audit. The subsequent authorized devnet deployment, exact shipped scope and live verification are recorded in the [rollout report](rollout/ROLLOUT.md). Statements below about undeployed changes describe that original audit checkpoint. Existing unrelated work in the frontend, Keeper and program repositories was preserved.

**Original deployment prerequisite (resolved for all 15 eligible configs in the rollout):** the oracle account allocation was 16 bytes too small, causing the 60th observation to fail serialization. The fix retains all 60 observations and adds an authorized resize from 1,765 to 1,781 bytes for existing undersized accounts. Deploying new code alone cannot resize them. Local fixtures verify wrong-authority rejection, rent top-up, unchanged existing state and successful observations 60/61. No live migration had been sent at this original checkpoint; the later authorized rollout completed all 15 eligible resizes. A devnet scan found 18 accounts with this undersized layout: 15 passed current-layout, PDA and owning-market authority checks; three reference missing markets and need intended-status review. One additional 1,733-byte account has an older schema and is excluded. Observed histories held zero or three samples, so no live 60th-observation outage is claimed. See the [migration runbook](oracle-migration.md) and [candidate ledger](evidence/oracle-migration-candidates.csv).

## Changes and quality preservation

- **Pool arithmetic:** carry the exact integer price recurrence through bins in Rust and TypeScript. Rust comparison covers 53,750 identical cases across quotes, execution and mutated reserves. TypeScript compares 10,000 input cases in both directions with the frozen reference. No floating-point approximation or changes to rounding, saturation, slippage or financial eligibility rules.
- **Frontend derivations:** a bounded 512-entry cache coalesces simultaneous derivations and evicts failed promises. Keys include program IDs, seeds, owners and token programs. It stores immutable addresses only.
- **Market roster:** shared market/health reads and memoized rows reduce repeated work. Collateral detail components mount when their native disclosure opens; their data remains prewarmed. All 14 market disclosures were exercised. Observed first opening took about 30–47 ms without a new data-loading delay.
- **Yield feed:** the server filters the full upstream catalogue and returns only the same selected rate/venue and source timestamp. Client freshness follows the upstream fetch time, so the server cache cannot silently extend the previous ten-minute freshness window. Reads coalesce, have deadlines, and retry only transient failures. Failure returns an error rather than stale data disguised as current.
- **Visibility and feedback:** the shared clock stops its interval when hidden and immediately recomputes when visible. Transaction tracking records preparation, wallet, submission and confirmation phase durations in existing events without another network request. The reconnect fix restores expected wallet behavior.
- **Keeper scheduling:** synchronous oracle, readiness and settlement boundaries yield the Tokio worker while retaining sequential financial execution, journaling and unknown-outcome protection. A one-worker synthetic test reduced an unrelated 10 ms timer's observed delay from about 101 ms to 11 ms during a 100 ms blocking operation.
- **Settlement discovery:** confirmed account notifications wake authoritative HTTP reads, with observed-slot fencing, scan coalescing, bounded reconnection and the existing polling fallback. A localhost protocol fixture measured event-to-wake at 0.962 ms. Notification data never supplies trade prices or balances.
- **Telemetry reads:** fetch newest batches until the required suffix is complete. Stream/day listing now follows continuation tokens beyond 1,000 objects. Incomplete pages, repeated cursors, unavailable batches, deadlines or resource bounds fail explicitly; downloads no longer silently skip missing batches.
- **Program correctness under real SBF execution:** internal Meteora helpers corrupted trailing scalar arguments under the SBF compiler. Borrowed parameter structs now preserve the values; actual initialization, add/remove liquidity, claim and close CPIs pass, including negative-bin and exact serialized-argument checks. The separate oracle allocation fix prevents a full observation ring from failing. Neither fix changes public trade math, slippage or risk-window length. [Regression evidence and migration requirements](runtime-coverage.md#controlled-sbf-execution-and-correctness-regressions).

No image-resolution, shader-quality, typography or animation-rate reduction was introduced by this audit. Existing visual behavior remains the reference. The existing homepage already stops its WebGL/rAF work offscreen and honors reduced motion; both were verified rather than claimed as new changes.

## Browser coverage and methodology

- Cold-load sweep: **23 route entries**, each in a fresh isolated browser context, 4× CPU and Fast 4G. All document loads returned 200; first contentful paint ranged from 588 to 1,040 ms in that sweep. This sweep preceded the final confirmation-loop and concurrent analytics edits. Alias redirects are included as route entries. A document 200 does not establish that every data dependency succeeded.
- Final-build repeated before/after observations: three samples each for `/pools`, `/mint`, and `/pools/AAPL`. Separate warm-reload traces are explicitly marked warm.
- Responsive review: seven routes at 1440, 768 and 375 px. Screenshots and DOM checks show no page-level horizontal overflow in those states. Native selects, disclosures, wallet dialogs, input extremes, filters, chart retry, navigation and empty-form validation were exercised.
- Action ledger: **608 recorded attempts**, including 447 timed attempts, three keyboard-focus observations and 158 unmeasured attempts. Repeated states and harness misses are retained. This is not 608 unique actions and does not imply exhaustive execution coverage. Supplemental runs corrected stale locators and exercised all 14 market disclosures and asset choices.
- Sitemap: 77 URLs, three localhost HTTP reads each, all 200. These are server response measurements, not browser hydration or data-ready measurements.
- Warm client navigation: route-heading appearance was measured separately from account readiness. Selected navigation observations were roughly 305–954 ms; the first pools navigation was 864 ms. The mobile menu took 141 ms to the two-frame marker, with visible keyboard focus preserved.

The interaction proxy starts at actual input and stops after two animation frames. A separate mutation observer records first DOM feedback. These are not field INP, and neither alone proves that an asynchronous action has semantically completed. Wallet success and settlement use explicit UI states. ## Remaining limits and bottlenecks

1. **Oracle eligibility dominates committed trades.** The Keeper's 15-second oracle cadence also defines a 60-sample, 15-minute risk window. Increasing frequency alone changes financial behavior. Faster safe settlement requires preserving that risk window and proving the resulting oracle semantics; this audit retains the existing rule and adds phase telemetry to separate eligibility from discovery and confirmation.
2. **Public RPC throttling is visible to users.** One test spent about ten seconds waiting after a 429. Local arithmetic improvements cannot remove upstream throttling. Measure a configured production RPC under load before changing provider or retry policy.
3. **Historical chart success is unmeasured locally.** `/api/pyth-ohlcv` returns 503 without the required local configuration. Error/retry rendering was exercised; an error response is not a successful chart benchmark.
4. **Production Keeper improvements are not yet timed.** There is no public Keeper domain in the inspected deployment. All 13 HTTP routes were measured in a local empty-network fixture; populated-state latency and contention remain unmeasured. Live CPU/memory samples indicate low average CPU use, not a saturated service. New scheduling and subscriptions need an after-deploy comparison.
5. **Privileged and external integrations need distinct fixtures.** The runtime ledger distinguishes successful SBF scenarios, historical/live receipts, expected guard failures and source-only inspection. Local fixtures now exercise real Meteora and yield-provider CPI; this establishes successful execution and CUs, not live RPC, wallet or production-liquidity latency. Authorized admin browser workflows remain distinct from local signed instruction fixtures. Privacy is intentionally disabled in the current application, as documented in [PRIVACY.md](../../frontend/PRIVACY.md). This audit's read-only public RPC/indexer/prover smoke check passed in 967 ms, with individual response-header times of 60–333 ms. It did not produce a private proof or move funds. Prior funded testing documented a private-spend failure at the external indexer; no completed private-transfer/withdrawal timing is claimed. [Current readiness measurement](../../frontend/docs/performance-audit/privacy-readiness.json).
6. **Heap results have a finite observation window.** Forty scroll cycles kept DOM counts at 1,534 on the homepage and 846 on pools. After ten warmup cycles, the next 30 retained about 0.52 MB and 0.47 MB respectively, including final idle measurements. Snapshots attribute most growth to compiled code/browser caches. A separate JIT-disabled diagnostic controlled for compilation: eight measured cycles stayed at 13.49–13.52 MB on home and 12.81–12.83 MB on pools, with final snapshot changes of −0.139 MB and +0.067 MB. This supports bounded application retention in the tested paths; it is not proof about every route or arbitrarily long sessions. No product JIT setting was changed. [Extended run](../../frontend/docs/performance-audit/retention-soak), [snapshot attribution](../../frontend/docs/performance-audit/retention), [JIT control](../../frontend/docs/performance-audit/retention-jitless).
7. **Supporting services:** the faucet service's first health read took 8.87 seconds while sleeping; warm reads were 249–273 ms. Its synchronous subprocess workflow can block health/debug requests. No CAPTCHA automation or airdrop workflow was invoked for that service. Discord read latency was sampled without posting messages; message delivery and history snapshots were not benchmarked as completed workflows.

## Validation and reproduction

Frontend: 278 tests across 57 files pass, including exact quote parity, address-cache behavior, yield selection/freshness, confirmation timing/guards and wallet-name parsing. The final production build and TypeScript check pass. Focused lint checks pass for changed frontend code. Existing SDK boundary/generation checks pass against the supplied IDLs; fresh Rust IDLs exposed separate admin-only drift, tracked in the runtime audit. These checks are not a clean-tree assertion: the workspace already contained substantial unrelated edits. The final build includes concurrent analytics/trading edits and has a matching before/after source manifest: [source fingerprint](../../frontend/docs/performance-audit/final-source-after.json), [build log](../../frontend/docs/performance-audit/build-final-confirmation.txt).

Signed local SBF coverage includes all 116 instruction entrypoints in 168 scenarios, replayed five times (840 transactions), with stable input hashes and compute units. Expected guards and the deprecated getter are identified separately from successful operations. This does not establish every business branch or live service latency. Runtime validation and instruction/task/endpoint coverage are maintained in [runtime-coverage.md](runtime-coverage.md). Fresh SBF binaries and source manifests are isolated under `/tmp/continuum-performance-sbf`; evidence records their hashes. The shared local fixture runner has no RPC transport, verifies signatures, and never submits an admin transaction to a public cluster.

R2 pagination validation adds nine passing Keeper tests plus two standalone response-parser tests. A three-page, 2,501-key fixture reaches the newest batch; continuation encoding, missing pages, repeated cursors and bounds are checked. The read follows the [official S3 continuation-token contract](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html). Stream/day tail and download reads require complete pagination. The separate bucket-wide file index still has its existing 1,000-key cap; it must not be treated as a complete inventory. [Test output](evidence/r2-pagination-tests.txt).

Browser scripts in `frontend/scripts/performance-*.py` require the installed Chrome DevTools MCP executable via `--mcp`. They run sequentially, checkpoint results, and close their owned disposable browser. T3's collaborative preview remains the ordinary UI review surface; the isolated diagnostic browser supplies throttling, traces and heap snapshots. Signed wallet scripts require the private disposable-wallet fixture outside the repository and do not automatically repeat signed work. No private key or service credential belongs in an evidence artifact.

## UX decisions

**Doherty:** measure immediate feedback separately from chain completion, remove main-thread work, and show transaction progress promptly. **Jakob:** retain native disclosures/selects and familiar wallet behavior. **Tesler:** centralize expensive selection and shared reads while keeping required data ready for the user. **Aesthetic–Usability:** preserve the reviewed visual design and motion quality rather than exchanging them for a smaller performance number.
